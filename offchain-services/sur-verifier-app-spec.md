# مشخصات فنی کامل — اپلیکیشن همراه ولیدیتور (فرانت‌اند سرویس Verifier)

> این سند به‌تنهایی برای پیاده‌سازی کافی است. تمام API‌ها، صفحات، و جریان‌های کاری همین‌جا دقیق مشخص شده‌اند. رابط برنامه‌نویسی بک‌اند از `sur-verifier-service-spec.md` بخش ۸.۱ عیناً نقل شده — این سند فقط همان API را مصرف می‌کند، هیچ منطق تازه‌ای در بک‌اند لازم ندارد.

## ۱. نقش کلی

تنها رابط کاربری‌ای که یک ولیدیتور واقعی با آن سروکار دارد: ثبت‌نام، احراز موبایل/تلگرام، ثبت `nodeID`، و مشاهده‌ی وضعیت لحظه‌ای. بدون این اپ، مکانیزم لایوینس (که ماندگاری ولیدیتور در شبکه به آن وابسته است) هیچ راه ورودی برای کاربر واقعی ندارد.

## ۲. کاربر هدف

ولیدیتورهای بالقوه/فعلی — عمدتاً کاربران ایرانی، با سطح آشنایی فنی متغیر (از توسعه‌دهنده‌ی حرفه‌ای تا کسی که فقط یک کیف‌پول نصب کرده).

## ۳. تصمیم معماری: وب‌اپ واکنش‌گرا (Responsive Web App)، نه اپ بومی

**دلیل:** با توجه به بودجه‌ی محدود بازاریابی/توسعه (`sur-marketing-roadmap.md`)، یک وب‌اپ که روی موبایل هم درست کار کند، به‌مراتب سریع‌تر و ارزان‌تر از دو اپ بومی جدا (iOS + Android) قابل‌ساخت و نگه‌داری است. اگر بعداً تقاضای واقعی توجیه کرد، تبدیل به اپ بومی (یا بسته‌بندی با Capacitor/React Native WebView) یک فاز بعدی مجزاست، نه بخشی از این اسکوپ.

## ۴. پشته‌ی فنی

| لایه | انتخاب |
|---|---|
| فریم‌ورک | React (Next.js — برای SSR سریع‌تر صفحه‌ی اول و SEO بهتر صفحه‌ی وضعیت عمومی) |
| اتصال کیف‌پول | `wagmi` + `viem` (هماهنگ با پشته‌ی مشترک پروژه) |
| مدیریت state | React Query (برای کش/رفرش خودکار پاسخ‌های API) |
| استایل | Tailwind CSS |
| زبان رابط | فارسی (اصلی و تنها زبان فاز اول) |
| میزبانی | هر هاست استاتیک/Node.js معمولی — بدون نیاز خاص |

## ۵. صفحات و جریان کاری دقیق

### ۵.۱ صفحه‌ی ورود
- دکمه‌ی «اتصال کیف‌پول» (پشتیبانی از MetaMask و هر کیف‌پول سازگار با WalletConnect — از طریق `wagmi`).
- بعد از اتصال، اپ خودکار `GET /api/v1/challenge?ethAddress=<آدرس متصل>` را صدا می‌زند.
- پیام دریافتی را با `wagmi`'s `signMessage` امضا می‌کند — این پیام باید **دقیقاً همان متنی** باشد که سرویس برگردانده، بدون تغییر.
- ⚠️ الزام UX: پیام امضا باید در پنجره‌ی کیف‌پول خوانا و قابل‌اعتماد باشد (نه یک رشته‌ی هگزادسیمال خام) — سرویس Verifier طبق طراحی خودش، `message` را به‌صورت متن ساده‌ی خوانا برمی‌گرداند (مثال در بخش ۸.۱ همان سند: `"Sur Verifier — Sign to authenticate — nonce: <random> — expires: <ts>"`)؛ اپ نباید این متن را قبل از امضا تغییر دهد.
- امضا و آدرس در `localStorage` (یا `sessionStorage`، ترجیحاً `sessionStorage` برای امنیت بیشتر) ذخیره می‌شود تا در فراخوانی‌های بعدی همین نشست دوباره استفاده شود؛ چون هر `challenge` منقضی می‌شود (بخش ۸.۱: expiry کوتاه، مثلاً ۵ دقیقه)، اپ باید در صورت خطای ۴۰۱ از هر endpoint، خودکار یک `challenge` تازه بگیرد و دوباره امضا بخواهد.

### ۵.۲ صفحه‌ی ثبت‌نام (اولین بار، بعد از ورود موفق)
فرم با فیلدهای:
- شماره موبایل (اعتبارسنجی فرمت ایرانی: `09xxxxxxxxx`).
- آیدی تلگرام (فرمت `@username`).
- `nodeID` — بخش ثابت `enode://<هگز عمومی>@` بدون IP/پورت؛ فیلد باید توضیح کوتاه داشته باشد که این را از کجا پیدا کند (خروجی `admin_nodeInfo` روی نود خودشان، فیلد `enode`، فقط تا قبل از `@`).
- دکمه‌ی ثبت → `POST /api/v1/register` با `{ ethAddress, signature, nodeId, phone, telegramId }`.
- بعد از موفقیت، هدایت خودکار به صفحه‌ی وضعیت (۵.۴).

### ۵.۳ جریان تأیید کد (موبایل و تلگرام، هرکدام جدا ولی هم‌ساختار)
1. دکمه‌ی «ارسال کد تأیید» → `POST /api/v1/phone/request-otp` (یا معادل تلگرام).
2. نمایش فیلد ورود کد ۶رقمی + تایمر شمارش معکوس ۲دقیقه‌ای برای امکان ارسال دوباره.
3. ثبت کد → `POST /api/v1/phone/verify-otp` با `{ ethAddress, signature, code }`.
4. موفقیت → به‌روزرسانی فوری وضعیت نمایشی (بدون نیاز به رفرش صفحه — از طریق invalidate کردن کوئری React Query مربوط به `/status`).
5. خطا (کد اشتباه/منقضی) → پیام خطای فارسی واضح + امکان درخواست کد تازه.

### ۵.۴ صفحه‌ی وضعیت (صفحه‌ی اصلی بعد از تکمیل ثبت‌نام)
داده از `GET /api/v1/status/:ethAddress` (بدون نیاز به امضا، طبق طراحی سرویس):
- کارت «موبایل»: ✅/❌ + دکمه‌ی «تأیید کن» اگر هنوز نشده.
- کارت «تلگرام»: مشابه.
- کارت «لایوینس»: آخرین تأیید لایوینس (`lastLivenessConfirmation`، تبدیل‌شده به «چند دقیقه/ساعت پیش»)، و یک نشانگر رنگی بزرگ: سبز اگر `isCurrentlyLive === true`، قرمز اگر نه.
- دکمه‌ی «به‌روزرسانی nodeID» — باز کردن یک مودال با همان فیلد `nodeID` فرم ثبت‌نام، ارسال با `PUT /api/v1/node-id`.
- این صفحه باید هر ۶۰ ثانیه خودکار رفرش شود (`refetchInterval` در React Query) تا وضعیت لایوینس تازه بماند، بدون نیاز کاربر به رفرش دستی.

## ۶. مدیریت خطا (سطح رابط کاربری)

| خطا | رفتار اپ |
|---|---|
| کیف‌پول متصل نیست | نمایش صفحه‌ی ورود، بدون تلاش برای فراخوانی هیچ API |
| امضا رد شد (کاربر لغو کرد) | بازگشت به صفحه‌ی ورود، بدون پیام خطای ترسناک — فقط «برای ادامه باید پیام را امضا کنید» |
| `challenge` منقضی شده (۴۰۱ از هر endpoint) | خودکار یک `challenge` تازه بگیر و دوباره امضا بخواه، بدون این‌که کاربر را به صفحه‌ی اول برگرداند |
| خطای شبکه/سرور (۵۰۰) | پیام «مشکلی پیش آمد، دوباره تلاش کنید» + دکمه‌ی retry |
| فرمت نامعتبر موبایل/nodeID | اعتبارسنجی سمت کلاینت قبل از ارسال، پیام خطای فارسی زیر همان فیلد |

## ۷. ملاحظات امنیتی سمت فرانت‌اند

- امضا و آدرس هرگز در کوئری‌استرینگ URL قرار نگیرند — همیشه در body یا header.
- بعد از هر بار بستن تب/خروج، `sessionStorage` پاک می‌شود (رفتار پیش‌فرض مرورگر) — کاربر باید دوباره امضا کند؛ این یک تصمیم عمدی امنیتی است، نه یک نقص UX.
- هیچ کلید خصوصی هرگز در این اپ ذخیره یا لاگ نمی‌شود — همه‌ی امضاها از طریق کیف‌پول متصل (extension/WalletConnect) انجام می‌شوند، اپ هرگز به کلید خصوصی دسترسی ندارد.
