# راهنمای پیاده‌سازی برای Claude Code — اپلیکیشن ولیدیتور (رابط کاربری `ValidatorsRegistry`)

> **این سند برای چیست:** این یک بریف پیاده‌سازی مستقل است که مستقیماً می‌تواند به Claude Code داده شود تا اپلیکیشن را بسازد. این سند جایگزین `sur-verifier-app-spec.md` می‌شود — تمام محتوای آن (ورود با امضا، وریفای موبایل/تلگرام، صفحه‌ی وضعیت) اینجا حفظ شده، به‌علاوه‌ی یک بخش کاملاً تازه که در سند قبلی جا افتاده بود: **تراکنش‌های واقعی on-chain چرخه‌ی عمر ولیدیتور** (`requestMembership`, `requestExit`, `withdrawStake`) که تا امروز هیچ رابط کاربری‌ای نداشتند.
>
> **چرا این کشف مهم است:** `sur-verifier-app-spec.md` فقط ثبت‌نام در سرویس آف‌چین Verifier (موبایل/تلگرام/nodeID) را پوشش می‌داد. اما خودِ عضویت ولیدیتور — قفل‌کردن وثیقه (`requestMembership`, تابعی `payable` که سورن واقعی می‌گیرد) — یک تراکنش کاملاً جداگانه و مستقیم با قرارداد `ValidatorsRegistry.sol` است که در هیچ سندی طراحی UI نشده بود. بدون این تراکنش، کاربر اصلاً «متقاضی ولیدیتوری» نمی‌شود؛ همه‌ی باقی مراحل (احراز موبایل/تلگرام، لایوینس) بعد از آن معنا پیدا می‌کنند.

---

## ۰. نقش کلی و کاربر هدف

تنها رابط کاربری‌ای که یک ولیدیتور واقعی (بالقوه یا فعلی) با آن سروکار دارد: قفل‌کردن وثیقه و پیوستن به شبکه، احراز موبایل/تلگرام، مشاهده‌ی وضعیت لحظه‌ای، و در پایان کار، خروج و پس‌گرفتن وثیقه.

**کاربر هدف:** عمدتاً کاربران ایرانی، با سطح آشنایی فنی متغیر (از توسعه‌دهنده‌ی حرفه‌ای گرفته تا کسی که فقط یک کیف‌پول نصب کرده).

## ۱. روش اتصال به بلاک‌چین

| مورد | تصمیم |
|---|---|
| کتابخانه‌ی اصلی | **wagmi v2 + viem** |
| رابط اتصال کیف‌پول | **Reown AppKit** (`@reown/appkit` + `@reown/appkit-adapter-wagmi`) — نسخه‌ی فعلی و برندِ جدید WalletConnect (شرکت WalletConnect Inc. به Reown تغییر نام داد؛ پروتکل و SDK همان WalletConnect است، فقط با برند و SDK به‌روزتر). **از `@web3modal/*` قدیمی یا SDKهای دست‌ساز استفاده نشود.** |
| نیازمندی جانبی | یک Project ID از [cloud.reown.com](https://cloud.reown.com) (رایگان) + allow-list کردن دامنه‌ی واقعی دیپلوی؛ بدون این، relay هندشیک را رد می‌کند. |
| کیف‌پول‌های پشتیبانی‌شده | کیف‌پول‌های Injected (مثل MetaMask روی دسکتاپ/موبایل) + هر کیف‌پول سازگار با WalletConnect (با اسکن QR یا deep-link موبایل) — هر دو به‌صورت خودکار از طریق AppKit. |
| شبکه | شبکه‌ی سفارشی سور باید به‌صورت یک `chain` سفارشی در تنظیمات wagmi/AppKit تعریف شود (chainId، نام، واحد بومی «سورن»، آدرس RPC). این مقادیر باید از یک فایل پیکربندی متمرکز خوانده شوند، نه هاردکد پراکنده. |
| احراز هویت کاربر (لاگین) | **بدون رمز عبور** — دقیقاً الگوی قبلی: اتصال کیف‌پول → گرفتن `challenge` از سرویس Verifier (`GET /api/v1/challenge`) → امضای پیام با `signMessage` → ارسال امضا به بک‌اند. پیام امضا باید متن ساده‌ی خوانا باشد، نه هگز خام — این را سرویس Verifier همین‌طور برمی‌گرداند. |
| تراکنش‌های نوشتنی | `useWriteContract` / `useSimulateContract` استاندارد wagmi برای هر پنج تابع بخش ۵ زیر. هرکدام باید قبل از ارسال واقعی، از طریق `useSimulateContract` شبیه‌سازی شود تا خطاهای احتمالی (مثل مبلغ نادرست) پیش از باز شدن پنجره‌ی امضا به کاربر نشان داده شود. |

## ۲. منوبندی (معماری اطلاعات)

```
اپلیکیشن ولیدیتور سور
│
├── (قبل از اتصال کیف‌پول) صفحه‌ی ورود
│     └── دکمه‌ی «اتصال کیف‌پول»
│
└── (بعد از اتصال + امضا)
      ├── خانه / داشبورد وضعیت من      ← صفحه‌ی پیش‌فرض بعد از ورود
      │     ├── کارت وضعیت عضویت (ثبت‌نشده / در دوره‌ی آزمایشی / فعال / کنارگذاشته‌شده / در حال خروج)
      │     ├── کارت موبایل (تأیید/تأیید‌نشده)
      │     ├── کارت تلگرام (تأیید/تأیید‌نشده)
      │     └── کارت لایوینس (آخرین تأیید + نشانگر رنگی زنده/غیرزنده)
      │
      ├── پیوستن به شبکه               ← فقط اگر وضعیت = «ثبت‌نشده»
      │     └── فرم درخواست عضویت (بخش ۵.۱)
      │
      ├── تأیید هویت
      │     ├── تب موبایل (OTP)
      │     └── تب تلگرام (OTP)
      │
      ├── تنظیمات گره (Node)
      │     └── فرم به‌روزرسانی nodeID
      │
      ├── خروج از شبکه                 ← فقط اگر وضعیت = «فعال»/«آزمایشی»/«کنارگذاشته‌شده»
      │     ├── دکمه‌ی «درخواست خروج» (بخش ۵.۲)
      │     └── (بعد از پایان دوره‌ی انتظار) دکمه‌ی «برداشت وثیقه» (بخش ۵.۳)
      │
      └── راهنما / پرسش‌های متداول     ← توضیح enode/nodeID، دوره‌ی آزمایشی، لایوینس، وثیقه
```

نکته‌ی طراحی: منو باید بر اساس وضعیت واقعی کاربر (خوانده‌شده از قرارداد) پویا باشد — مثلاً «پیوستن به شبکه» اصلاً نباید بعد از عضویت موفق در منو دیده شود؛ «خروج از شبکه» فقط وقتی چیزی برای خروج هست ظاهر شود.

## ۳. آیا بک‌اند لازم است؟ بله — سرویس‌های لازم

این اپلیکیشن **به‌تنهایی با اتصال به بلاک‌چین کافی نیست**. دو نوع نیاز کاملاً جدا از هم وجود دارد:

### ۳.۱ نیازهایی که مستقیم با کیف‌پول/بلاک‌چین حل می‌شوند (بدون بک‌اند)
- درخواست عضویت (`requestMembership`)، درخواست خروج (`requestExit`)، برداشت وثیقه (`withdrawStake`) — همه مستقیماً تراکنش امضاشده با کیف‌پول کاربر روی قرارداد `ValidatorsRegistry`، بدون واسطه.

### ۳.۲ نیازهایی که فقط با یک بک‌اند حل می‌شوند
سرویس **Verifier** (قبلاً به‌طور کامل طراحی شده — `sur-verifier-service-spec.md`) باید از قبل در دسترس باشد. این اپلیکیشن هیچ منطق تازه‌ای در بک‌اند لازم ندارد، فقط این API موجود را مصرف می‌کند:

| نیاز | چرا نمی‌شود روی زنجیره حلش کرد |
|---|---|
| صدور و اعتبارسنجی `challenge` برای ورود بدون رمز | باید یک nonce یک‌بارمصرف و کوتاه‌عمر تولید و نگه‌داری شود |
| ارسال و تأیید کد OTP پیامکی | ارسال پیامک نیازمند اتصال به یک درگاه SMS واقعی است، نه چیزی که قرارداد بتواند انجام دهد |
| ارسال و تأیید کد OTP تلگرام | مشابه بالا، از طریق ربات تلگرام |
| گزارش لایوینس (`reportLiveness`) | یک سرویس با کلید عملیاتی `verifier` (نگه‌داری‌شده در HashiCorp Vault) باید واقعاً وضعیت sync/تولید بلاک نود را بیرون از زنجیره بررسی و گزارش کند — این اپلیکیشن فقط **نتیجه‌ی** این گزارش را می‌خواند، خودش گزارش نمی‌دهد |
| ذخیره‌ی nodeID/موبایل/تلگرام خام | این داده‌ها روی زنجیره ذخیره نمی‌شوند (فقط فلگ‌های بولی وریفای on-chain هستند)؛ داده‌ی خام در دیتابیس سرویس Verifier می‌ماند |

**نتیجه‌گیری برای Claude Code:** این اپلیکیشن فقط یک فرانت‌اند است که هم به قرارداد (برای تراکنش‌های چرخه‌ی عمر) و هم به API سرویس Verifier (برای احراز هویت/OTP/وضعیت) متصل می‌شود. هیچ سرویس بک‌اند تازه‌ای لازم نیست ساخته شود — سرویس Verifier از قبل کامل مشخص است (`sur-verifier-service-spec.md`، بخش ۸.۱ برای اسکیمای دقیق API).

## ۴. طراحی UI/UX (باید مدرن باشد)

- **پشته‌ی فرانت‌اند:** React (Next.js) + Tailwind CSS، مطابق پشته‌ی مشترک پروژه.
- **زبان و جهت:** فارسی، راست‌به‌چپ (RTL) به‌طور کامل — از جمله اعداد، آیکون‌های جهت‌دار (فلش‌ها)، و چیدمان فرم‌ها.
- **فونت:** یک فونت فارسی مدرن با وزن‌های متعدد (مثل Vazirmatn یا IRANSans‌ایکس) — نه فونت پیش‌فرض سیستم.
- **رنگ برند:** آبی بنیاد `#2F3690` به‌عنوان رنگ اصلی/تأکیدی؛ پس‌زمینه‌ی خنثی و روشن؛ سبز/قرمز استاندارد فقط برای نشانگرهای وضعیت (زنده/غیرزنده، تأییدشده/نشده) — نه برای عناصر برند.
- **الگوی بصری:** کارت‌محور (هر وضعیت = یک کارت مجزا با آیکون و رنگ وضعیت)، فاصله‌گذاری سخاوتمندانه، بدون شلوغی. اسکلت بارگذاری (loading skeleton) به‌جای اسپینر خام برای هر کارت.
- **موبایل-اول:** چون بخش زیادی از کاربران فقط از موبایل استفاده می‌کنند (طبق تصمیم قبلی پروژه)، طراحی باید از عرض موبایل شروع شود، نه دسکتاپ.
- **بازخورد تراکنش:** برای هر تراکنش (`requestMembership` و بقیه)، توالی وضعیت واضح نشان داده شود: «در حال آماده‌سازی» → «منتظر تأیید در کیف‌پول» → «در حال ثبت روی شبکه» → «موفق / ناموفق»؛ از یک کتابخانه‌ی toast مدرن (مثل `sonner`) استفاده شود، نه `alert()`.
- **مودال تأیید قبل از امضا (حیاتی برای `requestMembership`):** چون این تابع سورن واقعی قفل می‌کند، قبل از باز شدن کیف‌پول باید یک مودال تأیید صریح نشان داده شود: «شما در حال قفل‌کردن **X سورن** (Y سورن وثیقه + Z سورن کارمزد عضویت) هستید. این مبلغ دقیقاً لحظه‌ی ارسال از قرارداد خوانده شده است.» — با دکمه‌ی تأیید نهایی جدا از دکمه‌ی امضای کیف‌پول.
- **حالت تیره (اختیاری، ارزش افزوده):** اگر زمان اجازه داد، حالت تیره هم اضافه شود؛ اولویت با حالت روشن است.

## ۵. توابع قرارداد `ValidatorsRegistry.sol` مورد استفاده (منبع صحت: کد واقعی قرارداد)

### ۵.۱ درخواست عضویت — `requestMembership()` — `payable`
- **بدون آرگومان.** مبلغ پرداختی (`msg.value`) باید **دقیقاً برابر** `currentEntryThreshold() + currentMembershipFee()` باشد — هر مبلغ دیگری (حتی بیشتر) رد می‌شود.
- ⚠️ **نکته‌ی حیاتی UX:** این دو مقدار به‌صورت پیوسته و بر اساس تعداد ولیدیتورهای فعال رشد می‌کنند. اپلیکیشن باید این دو مقدار را **بلافاصله قبل از فعال‌کردن دکمه‌ی ارسال** (نه فقط هنگام بارگذاری صفحه) دوباره بخواند، تا اگر بین باز کردن فرم و کلیک نهایی یک ولیدیتور دیگر پیوسته باشد، تراکنش با خطای «مبلغ نادرست» رد نشود.
- بعد از موفقیت، وضعیت کاربر «Probation» (دوره‌ی آزمایشی) می‌شود — هنوز در `getValidators()` ظاهر نمی‌شود.
- خطای رایج: `"already registered"` اگر آدرس قبلاً وضعیتی غیر از `None` داشته باشد.

### ۵.۲ درخواست خروج — `requestExit()`
- بدون آرگومان، بدون پرداخت.
- فقط از وضعیت‌های Active / Probation / Demoted قابل‌فراخوانی است.
- بلافاصله ولیدیتور را از `getValidators()` حذف می‌کند (اگر فعال بود) و شمارش‌معکوس دوره‌ی انتظار خروج (`exitCooldown`) را آغاز می‌کند.
- رویداد `ExitRequested(validator, cooldownEnd)` — این `cooldownEnd` باید در UI به‌صورت تاریخ/شمارش‌معکوس خوانا نشان داده شود.

### ۵.۳ برداشت وثیقه — `withdrawStake()`
- فقط بعد از پایان `exitCooldown` (که از `requestExit` شروع شده) قابل‌فراخوانی است؛ در غیر این صورت خطای `"exit cooldown not elapsed"`.
- کل وثیقه‌ی قفل‌شده را مستقیم به آدرس کاربر برمی‌گرداند و رکورد کاربر را کامل پاک می‌کند (بازگشت به وضعیت `None` — امکان درخواست عضویت مجدد در آینده وجود دارد).

### ۵.۴ توابع فقط‌خواندنی برای نمایش وضعیت
| تابع | استفاده در UI |
|---|---|
| `getValidatorInfo(address)` | وضعیت فعلی، مقدار وثیقه‌ی قفل‌شده، زمان شروع دوره‌ی فعلی، آخرین تأیید لایوینس |
| `currentEntryThreshold()` | مبلغ وثیقه‌ی لازم برای عضویت تازه (نمایش زنده، رفرش هر ۳۰ ثانیه) |
| `currentMembershipFee()` | کارمزد عضویت لازم (همراه با بالا) |
| `isValidator(address)` | آیا کاربر همین الان ولیدیتور فعال و واجد پرداخت است |

> توابع `proposeParameterChange`/`voteParameterChange` (رأی‌گیری تمام‌ولیدیتوری روی پارامترهای امنیتی مثل دوره‌ی آزمایشی، آستانه‌ی غیرفعالی، درصد اسلش) **در این اپلیکیشن پیاده‌سازی نمی‌شوند** — این یک اقدام حکمرانی جمعی است، نه یک اقدام فردی چرخه‌ی عمر، و در سند `sur-governance-dashboard-claudecode-brief.md` (بخش پنل چهارم) طراحی شده است تا کنار سایر ابزارهای رأی‌گیری پروژه یک‌جا باشد. اگر بعداً تصمیم گرفته شد این پنل هم اینجا تکرار/لینک شود، فقط باید یک لینک ساده به داشبورد حکمرانی اضافه شود.

## ۶. مدیریت خطا

| خطا | رفتار اپ |
|---|---|
| کیف‌پول متصل نیست | نمایش صفحه‌ی ورود، بدون تلاش برای فراخوانی هیچ API/قرارداد |
| امضای پیام لاگین رد شد | بازگشت به صفحه‌ی ورود، پیام خنثی «برای ادامه باید پیام را امضا کنید» |
| `challenge` منقضی شده (۴۰۱ از API) | خودکار یک `challenge` تازه بگیر و دوباره امضا بخواه |
| `requestMembership`: مبلغ نادرست | پیام «مبلغ وثیقه تغییر کرده — مبلغ تازه را دوباره بررسی کنید» + دکمه‌ی رفرش خودکار مبلغ |
| `requestMembership`: قبلاً ثبت‌نام کرده | هدایت مستقیم به صفحه‌ی وضعیت به‌جای نمایش خطا |
| `withdrawStake`: دوره‌ی انتظار تمام نشده | نمایش شمارش‌معکوس دقیق باقی‌مانده به‌جای پیام خطای خام قرارداد |
| تراکنش در کیف‌پول رد شد | پیام خنثی «تراکنش لغو شد»، بدون تلاش خودکار مجدد |
| خطای شبکه/سرور Verifier (۵۰۰) | پیام «مشکلی پیش آمد، دوباره تلاش کنید» + دکمه‌ی retry |
| فرمت نامعتبر موبایل/nodeID | اعتبارسنجی سمت کلاینت پیش از ارسال |

## ۷. ملاحظات امنیتی

- امضا و آدرس هرگز در query string قرار نگیرند.
- بعد از بستن تب، `sessionStorage` نشست پاک شود — کاربر باید دوباره امضا کند (تصمیم عمدی امنیتی).
- هیچ کلید خصوصی در این اپ ذخیره/لاگ نمی‌شود — همه‌ی امضاها و تراکنش‌ها از طریق کیف‌پول متصل (extension/AppKit) انجام می‌شوند.
- قبل از هر تراکنش پرداختی (`requestMembership`)، مبلغ دقیق باید به‌صورت خوانا (نه فقط wei خام) به کاربر نشان داده شود.
