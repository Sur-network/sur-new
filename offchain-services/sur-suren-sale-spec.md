# مشخصات قرارداد فروش سورن (SurenSale) و سرویس آف‌چین گزارش پرداخت

> این سند دو چیز را توصیف می‌کند: قرارداد `SurenSale.sol` (کد کامل در `contracts/SurenSale.sol`)، و یک سرویس آف‌چین **جدید** (سومین سرویس آف‌چین پروژه، بعد از RewardRouter و Verifier) که واسط بین درگاه پرداخت بانکی و این قرارداد است.

---

## ۱. چرا این طرح — خلاصه‌ی تصمیم

پیشنهاد اصلی: به‌جای فروش کاملاً دستی (پرداخت بانکی + ارسال دستی سورن توسط بنیاد)، یک قرارداد هوشمند بسازیم که:
- **قیمت را مستقل و از `block.timestamp` محاسبه می‌کند** (طبق جدول ۳٪ رشد مرکب ماهانه‌ی از‌پیش‌تصمیم‌گرفته‌شده) — نه از ورودی گزارش‌دهنده.
- فقط **تأیید وقوع پرداخت** را از یک کلید عملیاتی (`paymentOracle`) می‌پذیرد — دقیقاً همان الگوی اعتماد `verifier`/`distributionOracle` که قبلاً در پروژه جا افتاده.
- به‌طور خودکار و بدون دخالت انسانی، سورن معادل را به خریدار می‌فرستد.

**مزیت مستقیم:** داده‌ی «چقدر فروخته شده» دیگر نیاز به یک دیتابیس داخلی جدا در بنیاد ندارد — کاملاً on-chain و شفاف است؛ داشبورد فروش (سند `sur-product-development-plan.md`) می‌تواند مستقیم از این قرارداد بخواند.

## ۲. معماری قرارداد `SurenSale.sol`

### چرا genesis-injected نیست
برخلاف شش قرارداد ساختاری، این قرارداد فقط به آدرس ثابت `FoundationDAO` وابسته است (برای اجازه‌ی چرخش کلید و برداشت باقی‌مانده)، نه برعکس — یعنی هیچ قرارداد دیگری از قبل نیازی به دانستن آدرس این قرارداد ندارد. پس با یک تراکنش دیپلوی معمولی (نه در `alloc` genesis) در هر زمانی که بنیاد آماده بود مستقر می‌شود.

### جدول قیمت — هاردکد، نه فرمول توان on-chain
```solidity
uint256[6] public monthlyPriceToman = [100, 103, 106, 109, 113, 116];
```
چون فقط ۶ نقطه‌ی ثابت داریم (نه یک منحنی پیوسته مثل منحنی هزینه‌ی ورود ولیدیتور)، هاردکدکردن جدول ساده‌تر و کم‌گس‌تر از پیاده‌سازی یک فرمول توان عمومی روی زنجیره است.

### امنیت کلیدی — چرا `paymentOracle` نمی‌تواند قیمت را دستکاری کند
`reportPayment` فقط `tomanAmount` و `paymentReference` می‌گیرد؛ قیمت همیشه با `currentPriceToman()` مستقل محاسبه می‌شود. یعنی حتی یک کلید کاملاً هک‌شده فقط می‌تواند **ادعای پرداخت** کند (و موجودی فعلی قرارداد را با قیمت واقعی بخرد/خالی کند) — هرگز نمی‌تواند سورن را ارزان‌تر از قیمت رسمی همان لحظه بفروشد.

### ⚠️ توصیه‌ی امنیتی حیاتی: تأمین مالی دوره‌ای، نه یک‌جا
بنیاد **نباید** کل ۲۰ میلیون سورن را یک‌جا به این قرارداد واریز کند. با تأمین مالی دوره‌ای (مثلاً ماهانه، فقط به‌اندازه‌ی نیاز پیش‌بینی‌شده‌ی همان ماه)، سقف زیان احتمالیِ یک کلید `paymentOracle` هک‌شده به همان مبلغ کوچک محدود می‌ماند، نه کل ۲۰ میلیون.

### چرخش کلید `paymentOracle`
از طریق فراخوانی عمومی `FoundationDAO.proposeExecute(...)` (که از قبل در `FoundationDAO.sol` وجود دارد — نیازی به تغییر آن قرارداد نیست) با calldata متناظر با `SurenSale.setPaymentOracle(newAddress)`. این مسیر **اکثریت ساده** است، نه دوسوم — چون با تأمین مالی دوره‌ای (بالا)، سقف ریسک این کلید محدود نگه داشته می‌شود. 🔶 اگر بعداً مبالغ تأمین‌شده در هر دوره بزرگ‌تر شد، این تصمیم باید بازبینی و احتمالاً به نصاب دوسوم (نیازمند افزودن یک نوع پیشنهاد جدید به `FoundationDAO.sol`) ارتقا یابد.

### تأمین مالی خودِ قرارداد
از طریق `FoundationDAO.proposeSendETH(description, SurenSaleAddress, amount)` — نصاب **دوسوم**، چون این خرج واقعی دارایی بنیاد است (طبق قاعده‌ی موجود در `FoundationDAO.sol`).

## ۳. سرویس آف‌چین جدید: PaymentReporter

سومین سرویس آف‌چین پروژه (بعد از RewardRouter و Verifier)، با همان الگوی طراحی: یک کلید عملیاتی در HashiCorp Vault، یک daemon کوچک، بدون رابط کاربری عمومی.

### نقش
گوش‌دادن به webhook تأییدیه‌ی درگاه پرداخت (مثلاً زرین‌پال یا هر درگاه ایرانی دیگر)، و بعد از تأیید واقعی پرداخت، فراخوانی `SurenSale.reportPayment(buyer, tomanAmount, paymentReference)`. علاوه‌بر این، دو اندپوینت HTTP مستقیم برای اپلیکیشن فروش هم ارائه می‌دهد (بخش «رابط API برای اپلیکیشن خرید» زیر) — یعنی PaymentReporter هم یک گیرنده‌ی webhook است و هم یک API کوچک برای فرانت‌اند، نه فقط یک daemon گوش‌به‌زنگ.

### جریان کاری
1. کاربر در «پرتال فروش سورن» (طراحی کامل UI در `sur-suren-sale-portal-claudecode-brief.md`) آدرس دریافت‌کننده‌اش را وارد/متصل می‌کند؛ فرانت‌اند با فراخوانی `POST /api/v1/purchase/initiate` (بخش زیر) از همین سرویس PaymentReporter یک نشست پرداخت می‌سازد و کاربر به درگاه پرداخت هدایت می‌شود.
2. بعد از پرداخت موفق، درگاه یک webhook به PaymentReporter می‌زند (شامل مبلغ و کد پیگیری).
3. PaymentReporter **مستقل و مجدد** از خودِ API درگاه پرداخت تأیید می‌کند که این پرداخت واقعاً موفق بوده (هرگز فقط به داده‌ی خودِ webhook اعتماد نمی‌کند — این یک الگوی امنیتی استاندارد در تمام یکپارچه‌سازی‌های درگاه پرداخت است).
4. `SurenSale.reportPayment(...)` را با کلید Vault امضا و ارسال می‌کند.
5. نتیجه (موفق/ناموفق) را لاگ می‌کند؛ در صورت خطا (مثلاً موجودی قرارداد کافی نیست)، هشدار پیجینگ فوری — چون یعنی کاربر پول داده ولی سورن نگرفته، نیازمند رسیدگی دستی فوری.
6. کاربر در همین حین، صفحه‌ی برگشت از درگاه را می‌بیند که با `GET /api/v1/purchase/status/:paymentReference` (بخش زیر) هر چند ثانیه یک‌بار وضعیت را پول می‌زند تا به نتیجه‌ی نهایی برسد.

### رابط API برای اپلیکیشن خرید

این دو اندپوینت، مستقیم توسط فرانت‌اند «پرتال فروش سورن» (`sur-suren-sale-portal-claudecode-brief.md`) فراخوانی می‌شوند — برخلاف webhook درگاه که فقط خودِ درگاه صدا می‌زند. هیچ سرویس تازه‌ای برای این‌ها لازم نیست؛ هر دو بخشی از همان daemon و همان کلید Vault موجود PaymentReporter هستند.

**شروع خرید**
```
POST /api/v1/purchase/initiate
Body: { "buyerAddress": "0x...", "tomanAmount": 5000000 }
→ { "gatewayRedirectUrl": "https://zarinpal.com/pg/StartPay/...", "paymentReference": "..." }
```
وظیفه:
1. اعتبارسنجی فرمت `buyerAddress` (آدرس معتبر EVM).
2. تولید یک `paymentReference` یکتا و ذخیره‌ی رکورد اولیه‌ی آن در جدول `payments` (زیر) با `status='pending'`.
3. درخواست ساخت تراکنش پرداخت از API درگاه (مثلاً زرین‌پال) با `paymentReference` به‌عنوان شناسه‌ی پیگیری.
4. برگرداندن آدرس هدایت درگاه به فرانت‌اند.

**پیگیری وضعیت خرید**
```
GET /api/v1/purchase/status/:paymentReference
→ { "status": "pending" | "reported" | "failed", "onchainTxHash": "0x..." | null }
```
مستقیم از جدول `payments` می‌خواند — همان چیزی که صفحه‌ی برگشت از درگاه هر چند ثانیه یک‌بار پول می‌زند تا وضعیت نهایی («سورن ارسال شد») را نشان دهد.

### داده‌های ذخیره‌شده (SQLite، هماهنگ با الگوی دو سرویس دیگر)
| جدول | ستون‌های کلیدی |
|---|---|
| `payments` | `payment_reference`, `buyer_address`, `toman_amount`, `gateway_status`, `onchain_tx_hash`, `status` (`pending`/`reported`/`failed`) |

### ⚠️ سناریوی حیاتی که باید صریح مدیریت شود
اگه گزارش on-chain (قدم ۴) به هر دلیلی fail بشه (مثلاً موجودی قرارداد در اون لحظه کافی نبوده)، **کاربر واقعاً پول داده ولی سورن نگرفته**. این وضعیت باید فوراً و به‌صورت پیجینگ (نه فقط لاگ) به تیم اطلاع داده بشه، نه این‌که منتظر چرخه‌ی بعدی بمونه — چون برخلاف RewardRouter/Verifier، اینجا یه نفر واقعی منتظر پول واقعی خودشه. صفحه‌ی وضعیت خرید (`GET /api/v1/purchase/status/:paymentReference` بالا) باید برای این حالت (`status: "failed"`) پیام واضح و غیرفنی نشان دهد، نه فقط کد خطا.

### امنیت
- کلید `paymentOracle` در HashiCorp Vault (سیاست کلی پروژه، طبق `sur-software-inventory.md`) — کاملاً جدا از کلیدهای `verifier` و `distributionOracle`.
- اعتبارسنجی دوباره‌ی مستقل هر پرداخت با API خودِ درگاه (نه اعتماد صرف به webhook).
