## ۴. حکمرانی: یک رابط، چند نقش

**واقعیت فعلی:** رابط حکمرانی (U2) یک برنامه با چند پنل است: بنیاد، خزانهٔ ولیدیتورها، هیأت‌مدیرهٔ ولیدیتورها و پارامترهای امنیتی. بک‌اند ندارد؛ همه‌چیز را از قراردادها می‌خواند و نقش هر کاربر را کیف‌پول و قراردادها تعیین می‌کنند.

**چهار نقش:**

| نقش | از کجا خوانده می‌شود |
|---|---|
| عضو بنیاد | `FoundationMembers` |
| عضو هیأت‌مدیرهٔ بنیاد | `FoundationDAO` (هیأت ۵ نفره) |
| ولیدیتور | `ValidatorsRegistry` |
| عضو هیأت‌مدیرهٔ ولیدیتورها | `ValidatorsBoard` (۵ نفر) |

یک نفر می‌تواند چند نقش داشته باشد.

**اصل:** پنهان‌کردن پنل یا لینک از غیرعضو فقط ظاهری است. دسترسی واقعی را قراردادها اجرا می‌کنند؛ تراکنش غیرعضو revert می‌شود. پس رابط هرچه نشان دهد امنیت عوض نمی‌شود. فقط وضوح و تجربهٔ کاربر عوض می‌شود. خواندن پیشنهادها و نتیجه‌ها برای همه آزاد می‌ماند (شفافیت).

**✅ تصمیم مالک (۲۰۲۶-۱۱-۲۵): گزینهٔ ب.** سه شکل ورود مطرح شد:

| گزینه | شرح | نظر |
|---|---|---|
| الف | یک رابط؛ پس از ورود، پنل هر نقشی که کاربر دارد نشان داده می‌شود. | ساده‌ترین؛ ولی آدرس جدا برای بنیاد و ولیدیتورها از بین می‌رود. |
| **ب** | کاربر ابتدا با کیف‌پول وارد می‌شود؛ لینک نقش‌هایش (یا هر چهار نقش) نمایش داده می‌شود و هر کدام را بخواهد باز می‌کند. | ✅ **انتخاب‌شده:** با `gov` به‌عنوان درگاه و `foundation.gov`/`validators.gov` سازگار است و پیام جداسازی حکمرانی را نگه می‌دارد. |
| ج | ابتدا لینک هر چهار نقش؛ بعد ورود؛ غیرعضو پیام «دسترسی ندارید» می‌بیند. | تجربهٔ ضعیف‌تر: کاربر نقشی را که ندارد انتخاب می‌کند و بعد رد می‌شود. |

**رفتار گزینهٔ ب:**

1. کاربر در `gov.surnet.org` با کیف‌پول وارد می‌شود.
2. رابط نقش‌های او را از قراردادها می‌خواند (جدول بالا) و برای هر نقش یک لینک نشان می‌دهد؛ اگر سه نقش داشته باشد سه لینک.
3. هر لینک به بخش همان نقش می‌رود (`foundation.gov` یا `validators.gov`) و کاربر هر کدام را خواست باز می‌کند.
4. اگر کاربر مستقیم آدرس بخشی را باز کند که نقشش را ندارد، پیام خنثی می‌بیند («این نقش را ندارید») و صفحهٔ خواندنی عمومی بدون ورود باز می‌ماند.

🔶 جزئیات کوچک: نمایش فقط نقش‌های خود کاربر (پیش‌فرض) یا هر چهار نقش با مشخص‌کردن نقش‌های او؛ پیش‌فرض را همان «فقط نقش‌های خود کاربر» گذاشتم.

**پیاده‌سازی:** یک کدبیس برای همهٔ میزبان‌ها؛ هر میزبان با پیکربندی ساخت فقط پنل‌های خودش را نشان می‌دهد. بریف `sur-governance-dashboard-claudecode-brief.md` فعلاً یک برنامهٔ واحد را توصیف می‌کند و باید طبق گزینهٔ ب به‌روز شود. کد رابط در `Deployments/GovernanceDashboard` است (بیرون از این مخزن؛ برای این سند خوانده نشده).

## ۵. توزیع نصب نود (GitHub، `dl`، `registry`)

✅ تصمیم مالک (۲۰۲۶-۱۱-۲۵): هم GitHub، هم `dl`، و رجیستری زیردامنهٔ خودش را دارد. ✅ رجیستری ایمیج روی سرور **داخل ایران** است.

| موضوع | قاعده |
|---|---|
| منبع اصلی | **GitHub:** کد، `genesis.json`، چک‌سام‌ها و Releaseهای امضاشده با برچسب. تاریخچهٔ شفاف می‌ماند. |
| آینه | **`dl.surnet.org`:** همان فایل‌ها با همان هش، برای ولیدیتورهای داخل ایران. فایل‌های `docker save` هم اینجاست (SHA256 و امضا) برای نصب بدون رجیستری. |
| اعتماد | هش‌ها در مستندات هم منتشر می‌شوند. ولیدیتور هش یا امضا را می‌سنجد؛ لازم نیست به آینه اعتماد کند. |
| ایمیج | **`registry.surnet.org`:** ولیدیتور فقط ایمیج پین‌شده با `@sha256:` را می‌کشد. ایمیج‌ها در CI با هش منتشرشده ساخته می‌شوند. این سرویس واقعی ایمیج روی سروری **داخل ایران** با دیسک کافی است، نه هاست اشتراکی. ایمیج Besu هم از همین رجیستری کشیده شود (کیت راه‌اندازی فعلاً از Docker Hub می‌کشد). ✅ نرم‌افزار: `registry:2` با nginx و **دو در**: ۵۰۰۰ فقط‌خواندنی و عمومی، ۵۰۰۱ نوشتن با ورود فقط برای CI و مدیر (کلاینت داکر روی یک در «خواندن عمومی و نوشتن با ورود» رمز نمی‌فرستد). برچسب تغییرناپذیر نیست؛ ولیدیتور با digest می‌کشد. کیت و آزمون: `registry-kit/`. |
| آزمون | چون رجیستری داخل ایران است، دسترسی GHCR از ایران برای ایمیج شرط نیست. دسترسی ولیدیتورها به GitHub (برای کد و فایل‌ها) آزموده نشده؛ `dl` برای همین آینه است. |

## ۶. نام‌های ثابت‌شده در اسناد و قیدهایشان

| نام | قید |
|---|---|
| `validator-nft.surnet.org` | `baseURI` اولیهٔ `ValidatorSeatNFT` است و در genesis می‌آید. فقط `FoundationDAO` با پیشنهاد `Execute` و `setBaseURI` می‌تواند آن را عوض کند (رویداد `BaseURIChanged`). پس باید همیشه بالا بماند. مسئول نگه‌داری و محتوای metadata هنوز مشخص نیست (🔶 `sur-master-open-items.md`). |
| `kms.surnet.org` | گواهی عمومی معتبر (Let's Encrypt)؛ یک پورت؛ مسیرهای API امضا گواهی کلاینت سنجاق‌شده را اجباری می‌کنند و مسیرهای وب نه (`sur-kms-spec.md` بخش ۱۱.۲). |
| `node.surnet.org` | در اسناد با پورت `8545` آمده است. تصمیم نهایی نود آرشیوی (`TRACE`، حالت ذخیره) هنگام طراحی آن نود گرفته می‌شود (RD-3، RD-24). |
| `boot-node.surnet.org` | فقط DNS و P2P؛ RPC و متریک آن نود هرگز زیر این نام باز نمی‌شود. enode شامل کلید عمومی نود است؛ اگر کلید نود عوض شود، enode و فایل‌های `bootnodes` ولیدیتورها هم عوض می‌شود. پیش‌نیاز: `discovery-enabled=true` (✅ تصمیم مالک ۲۰۲۶-۱۱-۲۵). |
| ↳ نام DNS در enode | ✅ **VERIFIED (۲۰۲۶-۱۱-۲۵، Besu 26.9.0، میزبان آزمون، `boot-node-kit/dns-enode-test.sh`، ۶ از ۶):** `bootnodes=["enode://<کلید>@boot-node.surnet.org:30303"]` پذیرفته می‌شود **فقط با دو پرچم** `--Xdns-enabled=true` و `--Xdns-update-enabled=true` (آزمایشی و پنهان در Besu). بدون پرچم، Besu بالا نمی‌آید («Invalid bootnode … Invalid enode URL syntax»). با پرچم‌ها: نود تازه به bootnode وصل شد؛ پس از عوض‌شدن IP بوت‌نود (همان کلید، همان نام، IP دیگر) هم نودِ تازه و هم نودی که از قبل وصل بود دوباره به IP تازه رسیدند. محدودیت آزمون: شبکهٔ docker با DNS داخلی همان‌جا (نه DNS واقعی با TTL)؛ فقط TCP/UDP داخلی؛ آدرسی که خود بوت‌نود اعلام می‌کند (`--p2p-host`) در آزمون IP بود و بعد از تغییر IP با دست عوض شد. |
| ↳ بعد از عوض‌شدن IP | کلید نود (`key`) باید همان بماند، وگرنه enode عوض می‌شود. روی خود بوت‌نود `SUR_P2P_HOST` (و `--p2p-host`) باید IP تازه شود و نود ری‌استارت شود؛ استفاده از نام DNS در `--p2p-host` آزموده نشد (🔶). رکورد DNS `boot-node.surnet.org` باید به IP تازه برود و TTL کوتاه (مثلاً ۳۰۰ ثانیه) داشته باشد. |

## ۷. گواهی، میزبانی و امنیت

- **سی‌پنل (AutoSSL):** تا جایی که می‌دانیم برای هر نام جدا گواهی می‌دهد و wildcard نمی‌دهد؛ هر زیردامنه (از جمله `identity.api` و `foundation.gov`) باید جداگانه در سی‌پنل تعریف شود. نام چندسطحی مشکلی ندارد.
- **گواهی فقط روی همان سرور نصب می‌شود.** سرویس‌هایی که روی سرور دیگر می‌نشینند (`rpc`، `node`، بک‌اندهای Go، سرور KMS، `registry`) گواهی خودشان را می‌خواهند، مثلاً با certbot و تأیید HTTP برای هر نام.
- **KMS:** گواهی جدا و مستقل؛ کلید یک گواهی گسترده روی سرور KMS نمی‌نشیند.
- **سی‌پنل برای DNS و رابط‌های استاتیک مناسب است.** هر API پشتش به یک سرور واقعی نیاز دارد.
- **`rpc`:** `admin`، `debug`، `trace`، `txpool` هرگز باز نشود. `trace` فقط روی `node` خصوصی است.
- **`node`:** فقط با IP مجاز یا mTLS.
- **`boot-node`:** گواهی نمی‌خواهد؛ فقط رکورد A (و در صورت IPv6 رکورد AAAA). فایروال: `30303` TCP و UDP باز؛ RPC (`8545`) و متریک (`9545`) بسته.
- **سربرگ‌ها و DNS:** رکورد CAA برای دامنه؛ HSTS برای همهٔ زیردامنه‌ها؛ کوکی روی دامنهٔ والد ممنوع.
- **دسترسی از ایران:** میزبانی `rpc` و `surplorer` برای کاربران داخل ایران جداگانه سنجیده شود (فیلتر و پوشش).
