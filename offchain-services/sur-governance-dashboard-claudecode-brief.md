# راهنمای پیاده‌سازی برای Claude Code — داشبورد حکمرانی سور

> **این سند برای چیست:** جایگزین و تکمیل‌شده‌ی `sur-governance-dashboard-spec.md` است — همان سه پنل قبلی (بنیاد/خزانه/هیأت) اینجا حفظ شده‌اند، به‌علاوه‌ی یک **پنل چهارم کاملاً تازه** که در سند قبلی جا افتاده بود: رأی‌گیری تمام‌ولیدیتوری روی پارامترهای امنیتی مستقیماً روی قرارداد `ValidatorsRegistry` (توابع `proposeParameterChange`/`voteParameterChange`) — این با پنل «هیأت‌مدیره‌ی ولیدیتورها» (که پارامترهای *اقتصادی* را از طریق `ValidatorsBoard` تغییر می‌دهد) کاملاً متفاوت و مکمل است، نه تکراری.

---

## ۰. نقش کلی و کاربر هدف

جایگزینی برای تعامل خام با قرارداد (مثل تب Write Contract در بلاک اکسپلورر) با یک رابط کاربری که پیشنهادهای باز را نشان می‌دهد، وضعیت نصاب را واضح می‌کند، و رأی‌دادن را به یک کلیک تبدیل می‌کند.

**سه گروه کاربر، در چهار بخش جدای همین داشبورد:**
1. **اعضای بنیاد** (۱۵ نفر) — تعامل با `FoundationDAO`.
2. **ولیدیتورهای فعال** — تعامل با `ValidatorsTreasury` (پیشنهاد/رأی خرج)، `ValidatorsBoard` (رأی تأییدی عضویت هیأت)، و **`ValidatorsRegistry`** (رأی روی پارامترهای امنیتی — پنل تازه).
3. **اعضای هیأت‌مدیره‌ی ولیدیتورها** (۵ نفر، زیرمجموعه‌ی گروه ۲) — اقدامات داخلی هیأت روی `ValidatorsBoard`.

## ۱. روش اتصال به بلاک‌چین

| مورد | تصمیم |
|---|---|
| کتابخانه‌ی اصلی | **wagmi v2 + viem** |
| رابط اتصال کیف‌پول | **Reown AppKit** (`@reown/appkit` + `@reown/appkit-adapter-wagmi`) — نسخه‌ی فعلی و برند به‌روزشده‌ی WalletConnect؛ همان یکپارچگی که در اپلیکیشن ولیدیتور و اپ احراز هویت استفاده می‌شود، برای یکدستی تجربه‌ی کاربری در کل اکوسیستم سور. |
| منبع ABI | مستقیم از خروجی کامپایل `contracts/*.sol` — نه بازنویسی دستی. |
| مدیریت state داده‌ی زنده | React Query با `refetchInterval` برای داده‌های تغییرپذیر (نصاب فعلی، پارامترهای اقتصادی) — هر ۳۰ ثانیه. |
| تراکنش‌ها | همه مستقیماً با کیف‌پول خودِ کاربر امضا می‌شوند — **هیچ سرویس واسط یا کلید مشترکی در این داشبورد دخیل نیست** (برخلاف اپ ولیدیتور که یک بک‌اند هم دارد). |

## ۲. منوبندی (معماری اطلاعات)

```
داشبورد حکمرانی سور
│
├── (قبل از اتصال) صفحه‌ی ورود ساده — «اتصال کیف‌پول»
│
└── (بعد از اتصال — منو بر اساس نقش واقعی کاربر پویا ساخته می‌شود)
      │
      ├── نمای کلی               ← وضعیت زنده‌ی مشترک (آستانه‌ی ورود، کارمزد عضویت، تعداد ولیدیتور فعال)
      │
      ├── پنل بنیاد                          [فقط اگر isMember(address) === true، وگرنه فقط حالت مشاهده]
      │     ├── پیشنهادهای باز
      │     └── + پیشنهاد تازه (افزودن/حذف عضو، ارسال سورن، ارسال ERC20، اجرای دلخواه)
      │
      ├── پنل خزانه‌ی ولیدیتورها              [فقط اگر isValidator(address) === true]
      │     ├── پیشنهادهای خرج باز
      │     └── + پیشنهاد خرج تازه
      │
      ├── پنل هیأت‌مدیره‌ی ولیدیتورها          [نمایش برای همه‌ی ولیدیتورها، اقدامات داخلی فقط برای اعضای هیأت]
      │     ├── رأی‌گیری تأییدی برای عضویت هیأت  (voteFor/unvoteFor — همه‌ی ولیدیتورها)
      │     └── اقدامات داخلی هیأت                (فقط اعضای هیأت — isBoardMember)
      │
      └── پنل پارامترهای امنیتی ولیدیتورها ✨تازه [فقط اگر isValidator(address) === true — رأی تمام‌ولیدیتوری]
            ├── پیشنهادهای باز پارامتر
            └── + پیشنهاد پارامتر تازه
```

هر پنل باید صراحتاً برچسب بزند «این پنل مخصوص کدام قرارداد است» تا کاربری که هم عضو بنیاد و هم ولیدیتور است گیج نشود که هر اقدام روی کدام قرارداد اجرا می‌شود.

## ۳. آیا بک‌اند لازم است؟ خیر — تماماً بر بلاک‌چین

این داشبورد **هیچ بک‌اند اختصاصی لازم ندارد**. تمام داده (پیشنهادهای باز، تعداد رأی، نصاب لازم) مستقیماً از توابع `view` قراردادها خوانده می‌شود و هر اقدام (رأی‌دادن، پیشنهاد‌دادن) مستقیماً یک تراکنش امضاشده با کیف‌پول کاربر است. تنها وابستگی غیرمستقیم:

- بلاک اکسپلورر (Blockscout) باید سورس هر شش قرارداد را وریفای کرده باشد — بدونش هم ABI را می‌شود مستقیم از artifact کامپایل گرفت، پس این وابستگی فقط برای **شفافیت عمومی** است، نه برای کارکرد خودِ داشبورد.

## ۴. طراحی UI/UX (باید مدرن باشد)

- **پشته:** React (Next.js) + Tailwind CSS، زبان فارسی، راست‌به‌چپ کامل، فونت فارسی مدرن (Vazirmatn/IRANSans‌ایکس)، رنگ برند `#2F3690`.
- **الگوی اصلی صفحه:** فهرست پیشنهادهای باز به‌صورت کارت، با **نوار پیشرفت رأی** برجسته روی هر کارت (رأی فعلی از نصاب لازم — همیشه از تابع on-chain مربوطه خوانده شود، هرگز هاردکد در فرانت‌اند، چون نصاب‌ها بین انواع پیشنهاد فرق دارند).
- **فرم‌های «پیشنهاد تازه»:** یک تب مجزا برای هر نوع پیشنهاد؛ فیلدها دقیقاً منطبق با پارامترهای تابع on-chain متناظر (بخش ۵ تا ۹).
- **هشدار برجسته برای «اجرای دلخواه» (`proposeExecute` در بنیاد):** چون این فرم داده‌ی هگز دلخواه on-chain اجرا می‌کند، باید پیش از ارسال، `data` را در یک ابزار decode ساده تلاش کند با ABI شناخته‌شده‌ی قراردادهای پروژه تطبیق دهد و نمایش دهد چه فراخوانی‌ای واقعاً رخ می‌دهد؛ اگر decode ناموفق بود، هگز خام کامل نمایش داده شود، پنهان نشود.
- **دکمه‌های اقدام باید کاملاً پنهان شوند (نه فقط غیرفعال)** اگر کاربر واجد شرایط نیست — این چک همیشه با یک خواندن on-chain (`isMember`/`isValidator`/`isBoardMember`) پیش از رندر فرم انجام شود.
- **بازخورد تراکنش:** توالی وضعیت واضح («در حال آماده‌سازی» → «منتظر امضا» → «در حال ثبت» → «موفق/ناموفق») با toast مدرن، نه `alert()`.

## ۵. پنل بنیاد (`FoundationDAO`)

### فهرست پیشنهادهای باز
برای هر پیشنهاد با `status == Pending`:
- نوع (`AddMember`/`RemoveMember`/`SendETH`/`SendERC20`/`Execute`) با برچسب فارسی.
- توضیح (`description`)، پیشنهاددهنده (`proposer`).
- نوار پیشرفت رأی: `votes` از `requiredVotesNow(pType)` (دوسوم برای `AddMember`/`RemoveMember`/`SendETH`، اکثریت ساده برای بقیه — همیشه از تابع خوانده شود).
- دکمه‌ی «رأی موافق» (فقط اگر `hasVoted(id, msg.sender) === false`) → `vote(proposalId)`.

### فرم پیشنهاد تازه (فقط اعضا — چک `isMember(address)`)
| تب | فیلدها | تابع |
|---|---|---|
| افزودن عضو | نام، آدرس | `proposeAddMember(description, name, account)` |
| حذف عضو | انتخاب از `getAllMembers()` | `proposeRemoveMember(description, account)` |
| ارسال سورن | آدرس مقصد، مبلغ (تبدیل به wei در کلاینت) | `proposeSendETH(description, to, amount)` |
| ارسال ERC20 | آدرس توکن، آدرس مقصد، مبلغ | `proposeSendERC20(description, token, to, amount)` |
| اجرای دلخواه ⚠️ | آدرس هدف، مبلغ، داده‌ی هگز | `proposeExecute(...)` — هشدار برجسته الزامی |

اطلاعات جانبی: تعداد اعضا (`getMemberCount()`)، موجودی بنیاد (`getEthBalance()`).

## ۶. پنل خزانه‌ی ولیدیتورها (`ValidatorsTreasury`)

### فهرست پیشنهادهای خرج باز
برای هر `Expenditure` با `executed == false`: گیرنده، مبلغ، توضیح، نصاب (`(activeValidatorCount/2)+1` — از `ValidatorsRegistry.requiredVotesNow()` خوانده شود)، دکمه‌ی رأی (`voteExpenditure(id)`) فقط اگر `ValidatorsRegistry.isValidator(msg.sender) === true`.

### فرم پیشنهاد خرج تازه
فقط ولیدیتورهای فعال: گیرنده، مبلغ، توضیح → `proposeExpenditure(to, amount, description)`.

اطلاعات جانبی: موجودی خزانه (`getBalance()`)، `smallBudgetCap` فعلی (فقط نمایشی).

---

## ۷. پنل هیأت‌مدیره‌ی ولیدیتورها (`ValidatorsBoard`)

### رأی‌گیری تأییدی عضویت هیأت (همه‌ی ولیدیتورهای فعال)
فهرست همه‌ی ولیدیتورهای فعال (`ValidatorsRegistry.getValidators()`) به‌عنوان کاندید، با تعداد رأی هرکدام (`getVotersFor(candidate).length`). دکمه‌ی «رأی موافق» (`voteFor`) یا «پس‌گرفتن رأی» (`unvoteFor`) بسته به `hasVotedFor[msg.sender][candidate]`؛ دکمه‌ی رأی غیرفعال اگر `getVotesOf(msg.sender).length >= 5`. نمایش برجسته‌ی ۵ عضو فعلی هیأت (`getBoardMembers()`). دکمه‌ی «به‌روزرسانی نتیجه» (`refreshBoard()` — permissionless).

### اقدامات داخلی هیأت (فقط اعضای هیأت — `isBoardMember`)
فهرست اقدامات باز با نوع (`RotateOracle`/`ApproveBudget`/`SetEntryThresholdBase`/`SetGrowthFactorPerValidator`/`SetMembershipFeeBps`/`RotateVerifier`)، نصاب `(boardSize/2)+1`، دکمه‌ی رأی (`voteAction(id)`). فرم ساخت اقدام تازه، یک تب برای هرکدام از شش نوع، با پارامترهای تابع `propose*` متناظر.

---

## ۸. پنل پارامترهای امنیتی ولیدیتورها ✨ (تازه — روی `ValidatorsRegistry` مستقیماً)

### چرا این پنل جداست از پنل هیأت (بخش ۷)
قرارداد `ValidatorsRegistry` حکمرانی‌اش را عمداً به دو مسیر مجزا تقسیم کرده:
- **پارامترهای اقتصادی ورود** (`entryThresholdBase`, `growthFactorPerValidator`, `membershipFeeBps`): فقط با رأی داخلی هیأت — همان بخش ۷.
- **همه‌چیز دیگر** (سقف نرخ درخواست عضویت، طول دوره‌ی آزمایشی، آستانه‌ی غیرفعالی، دوره‌ی بازیابی، درصد اسلش، دوره‌ی انتظار خروج): نیازمند **رأی اکثریت تمام ولیدیتورهای فعال** مستقیماً روی `ValidatorsRegistry`، نه بنیاد، نه هیأت — چون این‌ها مفروضات امنیتی خودِ مجموعه‌ی ولیدیتورهاست.

این تفاوت مسیر باید در UI کاملاً واضح باشد؛ بهترین راه، برچسب‌گذاری دو پنل مجزا با توضیح یک‌خطی زیر عنوان هرکدام (دقیقاً متن بالا، خلاصه‌شده).

### `enum ParamKey` (هشت مقدار — دقیقاً به همین ترتیب در قرارداد)
| کلید | معنی |
|---|---|
| `MaxEntriesPerWindow` | حداکثر تعداد درخواست عضویت مجاز در یک بازه‌ی زمانی |
| `EntryWindowSeconds` | طول همان بازه‌ی زمانی (ثانیه) |
| `ProbationPeriod` | طول دوره‌ی آزمایشی قبل از فعال‌سازی (ثانیه) |
| `MinLivenessConfirmationsToActivate` | حداقل تعداد تأیید لایوینس لازم برای خروج از دوره‌ی آزمایشی |
| `InactivityThreshold` | مدت غیبت که باعث کنارگذاشتن خودکار می‌شود |
| `RecoveryPeriod` | مدت لازم تأیید پیوسته‌ی لایوینس برای بازگشت بعد از کنارگذاشتن |
| `SlashBps` | درصد جریمه‌ی وثیقه هنگام کنارگذاشتن (از ۱۰۰۰۰ = صددرصد) |
| `ExitCooldown` | دوره‌ی انتظار بین درخواست خروج و برداشت وثیقه |

### فهرست پیشنهادهای باز
برای هر `ParamProposal` با `executed == false`: نام پارامتر (نگاشت `ParamKey` به برچسب فارسی خوانا از جدول بالا)، مقدار پیشنهادی (`newValue`)، تعداد رأی (`votes`) از نصاب لازم (`requiredVotesNow()` — همان `(activeValidatorCount/2)+1`)، پیشنهاددهنده و زمان ایجاد. دکمه‌ی «رأی موافق» (فقط اگر `paramHasVoted[id][msg.sender] === false` و فراخوان‌کننده `isValidator`) → `voteParameterChange(id)`.

### فرم پیشنهاد تازه (فقط ولیدیتورهای فعال)
انتخاب پارامتر از دراپ‌داون `ParamKey` (با توضیح یک‌خطی هرکدام از جدول بالا) + فیلد مقدار تازه → `proposeParameterChange(key, newValue)`. **نکته:** خودِ فراخوانی این تابع، اولین رأی پیشنهاددهنده را هم ثبت می‌کند (طبق کد قرارداد) — این باید در UI توضیح داده شود تا کاربر تعجب نکند که رأی خودش را نمی‌بیند دکمه‌ی «رأی» جدا.

### اطلاعات جانبی
مقادیر فعلی هر هشت پارامتر (خواندنی مستقیم از متغیرهای عمومی قرارداد) باید همیشه کنار فرم پیشنهاد نمایش داده شوند تا کاربر مقدار فعلی را قبل از پیشنهاد تغییر ببیند.

## ۱۰. مدیریت خطا

| خطا | رفتار |
|---|---|
| فراخوان‌کننده عضو/ولیدیتور/عضو هیأت نیست | دکمه‌های اقدام اصلاً نمایش داده نشوند |
| رأی تکراری | پیام فارسی «شما قبلاً رأی داده‌اید» از روی خطای برگشتی |
| تراکنش رد شد در کیف‌پول | پیام خنثی «تراکنش لغو شد» |
| نصاب هنوز کامل نشده بعد از رأی | «رأی شما ثبت شد، منتظر رأی بقیه» |
| پیشنهاد پارامتر: کلید تکراری با مقدار متفاوت پیشنهاد شده | هر پیشنهاد شناسه‌ی خودش را دارد؛ هشدار نرم «پیشنهاد مشابهی همین الان باز است» با لینک به آن |

## ۱۱. امنیت

- همه‌ی تراکنش‌ها مستقیم با کیف‌پول کاربر امضا می‌شوند — بدون سرویس واسط.
- فرم «اجرای دلخواه» باید هگز را decode یا کامل نمایش دهد (بخش ۴).
- پنل پارامترهای امنیتی باید تأکید کند این تغییرات مستقیماً روی مفروضات امنیتی شبکه اثر می‌گذارند — یک هشدار ملایم («این پارامتر امنیتی شبکه را تغییر می‌دهد») برای هر پیشنهاد تازه در این پنل مناسب است.
