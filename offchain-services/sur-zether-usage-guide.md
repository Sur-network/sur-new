# راهنمای کاربرد `SurZether.sol` — تراکنش‌های محرمانه روی سور

> این سند مکمل `sur-zether-confidential-transfers-proposal.md` است — همان سند را برای معماری کلی، ریسک‌ها، و برنامه‌ی اجرا ببینید. این سند فقط «چطور از قرارداد استفاده کنیم» را توضیح می‌دهد.

⚠️ **یادآوری:** این قرارداد، همان‌طور که در بالای خودِ فایل `SurZether.sol` نوشته شده، **آماده‌ی دیپلوی روی شبکه‌ی واقعی نیست** — `IZetherVerifier` باید با یک پیاده‌سازی رسمی و آدیت‌شده جایگزین شود. این راهنما فرض می‌کند آن مرحله (بخش ۸ سند پیشنهاد) قبلاً انجام شده.

---

## ۱. دیپلوی

```solidity
// آدرس یک پیاده‌سازی واقعی و آدیت‌شده‌ی IZetherVerifier — نه این فایل، بلکه چیزی که طبق
// بخش ۸ سند پیشنهاد انتخاب/فورک/آدیت شده است.
SurZether zether = new SurZether(REAL_AUDITED_VERIFIER_ADDRESS);
```

این یک دیپلوی معمولی است — دقیقاً مثل هر دپ دیگری روی سور، بدون نیاز به جایگاه ویژه در genesis یا اجازه از بنیاد/ولیدیتورها (بخش ۲ سپیدنامه).

## ۲. گردش کار کامل کاربر — چهار قدم

### قدم ۱: ثبت‌نام (`register`)

کاربر یک جفت‌کلید Zether (جدا از کلید کیف‌پول Ethereum‌اش) در کلاینت خودش تولید می‌کند، سپس کلید عمومی‌اش را روی زنجیره ثبت می‌کند:

```javascript
// سمت کلاینت — با کتابخانه‌ی سمت کلاینت (بخش ۶ سند پیشنهاد)
const { pubKeyX, pubKeyY, privateKey } = zetherClient.generateKeyPair();
// privateKey فقط در کیف‌پول کاربر می‌ماند، هرگز به هیچ سروری فرستاده نمی‌شود

await zether.write.register([pubKeyX, pubKeyY]);
```

### قدم ۲: واریز (`fund`) — تبدیل سورن معمولی به موجودی رمزشده

```javascript
const accountKey = zetherClient.computeAccountKey(pubKeyX, pubKeyY);
await zether.write.fund([accountKey], { value: parseEther('1000') }); // ۱۰۰۰ سورن
```

⚠️ همان‌طور که در سند پیشنهاد آمده، **مبلغ این تراکنش عمومی و قابل‌مشاهده است** — این بخشی از طراحی اصلی Zether است، نه یه محدودیت این پیاده‌سازی. محرمانگی فقط از تراکنش *بعدی* (قدم ۳) شروع می‌شود.

### قدم ۳: انتقال محرمانه (`transfer`)

```javascript
// کل این محاسبه سمت کلاینت انجام می‌شود — قرارداد فقط نتیجه‌ی نهایی را می‌بیند
const { deltaFrom, deltaTo, proof } = await zetherClient.buildTransfer({
  senderPrivateKey,
  senderBalance: await zether.read.balances([senderAccountKey]),
  receiverPubKey: { x: receiverPubKeyX, y: receiverPubKeyY },
  amount: parseEther('50'), // این عدد هرگز روی زنجیره نمی‌رود
});

await zether.write.transfer([
  senderAccountKey,
  receiverAccountKey,
  deltaFrom,
  deltaTo,
  proof,
]);
```

نتیجه: روی اکسپلورر، همه می‌بینند یک `Transferred` رخ داده بین دو `accountKey`، ولی هیچ‌کس (نه حتی ولیدیتورها) مبلغ ۵۰ سورن را نمی‌بیند.

### قدم ۴: خروج (`burn`) — بازگشت به سورن معمولی

```javascript
const { amount, proof } = await zetherClient.buildBurn({
  privateKey: senderPrivateKey,
  balance: await zether.read.balances([senderAccountKey]),
  withdrawAmount: parseEther('50'),
});

await zether.write.burn([senderAccountKey, amount, proof]);
// سورن مستقیم به آدرس msg.sender (فرستنده‌ی همین تراکنش) برمی‌گردد
```

⚠️ مبلغ برداشت‌شده در این مرحله دوباره عمومی می‌شود — طبیعی و ذاتی هر سیستم محرمانه‌ای که در نهایت باید به دارایی قابل‌مصرف در دنیای عمومی تبدیل شود.

## ۳. جدول خلاصه — چه‌چیزی عمومی می‌ماند، چه‌چیزی محرمانه

| رویداد | چه‌کسی چه‌چیزی می‌بیند |
|---|---|
| `register` | همه می‌بینند این کلید عمومی ثبت شده — بدون اطلاعات مالی |
| `fund` | همه مبلغ واریزی را می‌بینند (طراحی عمدی Zether) |
| `transfer` | همه می‌بینند تراکنشی بین دو حساب رخ داده؛ **هیچ‌کس مبلغ را نمی‌بیند** |
| `burn` | همه مبلغ برداشتی را می‌بینند؛ موجودی *باقی‌مانده*‌ی حساب همچنان محرمانه است |

## ۴. هزینه‌ی تقریبی هر عملیات

طبق بخش ۷ سند پیشنهاد، `transfer` و `burn` به‌خاطر بررسی اثبات دانش-صفر محاسباتی سنگین‌تر از یک انتقال ساده‌ی سورن هستند. عدد دقیق فقط بعد از انتخاب نهایی پیاده‌سازی مرجع (بخش ۸ سند پیشنهاد) قابل‌محاسبه است — این عدد باید پیش از عرضه‌ی عمومی این قابلیت، به‌صراحت در مستندات توسعه‌دهنده اعلام شود.

## ۵. برای توسعه‌دهنده‌ای که می‌خواهد این قرارداد را در دپ خودش استفاده کند

- می‌توانید مستقیماً به آدرس دیپلوی‌شده‌ی `SurZether` (بعد از این‌که بنیاد یا هرکسی آن را دیپلوی کرد) ارجاع دهید — نیازی به دیپلوی نسخه‌ی خودتان نیست، مگر بخواهید verifier متفاوتی استفاده کنید.
- `accounts` و `balances` هر دو `public` هستند — هر قراردادی می‌تواند وضعیت ثبت‌نام یا موجودی رمزشده‌ی خام (نه مبلغ واقعی) هر حسابی را بخواند.
- برای build کردن `proof` در دپ‌های خودتان، از همان کتابخانه‌ی سمت کلاینت استفاده کنید (بخش ۶ سند پیشنهاد) — این منطق را در قرارداد خودتان بازتولید نکنید.
