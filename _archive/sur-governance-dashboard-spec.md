# مشخصات فنی کامل — داشبورد حکمرانی (بنیاد و ولیدیتورها)

> این سند به‌تنهایی برای پیاده‌سازی کافی است. تمام توابع قرارداد، پارامترها، و جریان‌های کاری از قراردادهای نهایی پروژه (`contracts/`) عیناً استخراج شده‌اند.

## ۱. نقش کلی

جایگزینی برای تعامل خام با قرارداد (مثل تب Write Contract در بلاک اکسپلورر) با یک رابط کاربری که پیشنهادهای باز را نشان می‌دهد، وضعیت نصاب را واضح می‌کند، و رأی‌دادن را به یک کلیک تبدیل می‌کند.

## ۲. کاربر هدف — سه گروه با نیازهای متفاوت، در سه بخش جدای همین داشبورد

1. **اعضای بنیاد** (۱۵ نفر) — تعامل با `FoundationDAO`.
2. **ولیدیتورهای فعال** — تعامل با `ValidatorsTreasury` (پیشنهاد/رأی خرج) و `ValidatorsBoard` (رأی‌گیری تأییدی عضویت هیأت).
3. **اعضای هیأت‌مدیره‌ی ولیدیتورها** (۵ نفر، زیرمجموعه‌ی گروه ۲) — اقدامات داخلی هیأت روی `ValidatorsBoard`.

## ۳. پشته‌ی فنی

| لایه | انتخاب |
|---|---|
| فریم‌ورک | React (Next.js) |
| اتصال کیف‌پول و خواندن/نوشتن قرارداد | `wagmi` + `viem` |
| مدیریت state | React Query، با `refetchInterval` برای داده‌های زنده (نصاب، پارامترهای اقتصادی) |
| استایل | Tailwind CSS |
| زبان رابط | فارسی |
| منبع ABI | مستقیم از خروجی کامپایل `contracts/*.sol` (نه بازنویسی دستی) |

## ۴. بخش ۱ — پنل بنیاد (`FoundationDAO`)

### ۴.۱ فهرست پیشنهادهای باز
برای هر پیشنهاد با `status == Pending`، نمایش:
- نوع پیشنهاد (`AddMember` / `RemoveMember` / `SendETH` / `SendERC20` / `Execute`) — با برچسب فارسی خوانا.
- توضیح (`description`).
- پیشنهاددهنده (`proposer`).
- نوار پیشرفت رأی: `votes` از `requiredVotesNow(pType)` — این تابع مستقیم روی قرارداد صدا زده می‌شود تا نصاب دقیق (دوسوم برای `AddMember`/`RemoveMember`/`SendETH`، اکثریت ساده برای بقیه) همیشه درست نمایش داده شود، نه هاردکد در فرانت‌اند.
- دکمه‌ی «رأی موافق» (فقط اگر `hasVoted(id, msg.sender) === false`) → فراخوانی `vote(proposalId)`.

### ۴.۲ فرم ساخت پیشنهاد تازه (فقط برای اعضا — چک `isMember(address)` قبل از نمایش فرم)
تب جدا برای هر نوع:
- **افزودن عضو:** فیلد نام + آدرس → `proposeAddMember(description, name, account)`.
- **حذف عضو:** انتخاب از لیست اعضای فعلی (`getAllMembers()`) → `proposeRemoveMember(description, account)`.
- **ارسال سورن:** فیلد آدرس مقصد + مبلغ (به سورن، تبدیل به wei در کلاینت) → `proposeSendETH(description, to, amount)`.
- **ارسال توکن ERC20:** فیلد آدرس توکن + آدرس مقصد + مبلغ → `proposeSendERC20(description, token, to, amount)`.
- **اجرای دلخواه:** فیلد آدرس هدف + مبلغ + داده‌ی هگز (`data`) — این فرم باید یک هشدار برجسته نمایش دهد («این عملیات پیشرفته است، کد را خودتان تأیید کنید»)، چون داده‌ی دلخواه on-chain اجرا می‌شود.

### ۴.۳ اطلاعات جانبی صفحه
- تعداد اعضا (`getMemberCount()`).
- موجودی فعلی بنیاد (`getEthBalance()`).

## ۵. بخش ۲ — پنل خزانه‌ی ولیدیتورها (`ValidatorsTreasury`)

### ۵.۱ فهرست پیشنهادهای خرج باز
مشابه ۴.۱، برای هر `Expenditure` با `executed == false`:
- گیرنده، مبلغ، توضیح.
- نصاب: `votes` از تعداد لازم (`(activeValidatorCount/2)+1` — این عدد را از `ValidatorsRegistry.requiredVotesNow()` بخوان، چون همان مرجع محاسبه است).
- دکمه‌ی رأی (فقط اگر فراخوان‌کننده `ValidatorsRegistry.isValidator(msg.sender) === true` باشد) → `voteExpenditure(id)`.

### ۵.۲ فرم پیشنهاد خرج تازه
فقط برای ولیدیتورهای فعال (چک `isValidator`): فیلد گیرنده + مبلغ + توضیح → `proposeExpenditure(to, amount, description)`.

### ۵.۳ اطلاعات جانبی
- موجودی فعلی خزانه (`getBalance()`).
- `smallBudgetCap` فعلی (فقط نمایشی — تغییرش فقط از طریق هیأت است، بخش ۶).

## ۶. بخش ۳ — پنل هیأت‌مدیره‌ی ولیدیتورها (`ValidatorsBoard`)

### ۶.۱ رأی‌گیری تأییدی برای عضویت هیأت (برای همه‌ی ولیدیتورهای فعال)
- فهرست همه‌ی ولیدیتورهای فعال (`ValidatorsRegistry.getValidators()`) به‌عنوان کاندیدهای بالقوه، با تعداد رأی فعلی هرکدام (`getVotersFor(candidate).length`).
- برای هرکدام، اگر فراخوان‌کننده از قبل رأی داده (`hasVotedFor[msg.sender][candidate]`)، دکمه‌ی «پس‌گرفتن رأی» (`unvoteFor`)؛ وگرنه دکمه‌ی «رأی موافق» (`voteFor`) — غیرفعال اگر `getVotesOf(msg.sender).length >= 5` (سقف `MAX_VOTES_PER_VOTER`).
- نمایش برجسته‌ی ۵ عضو فعلی هیأت (`getBoardMembers()`) در بالای همین صفحه.
- دکمه‌ی «به‌روزرسانی نتیجه» (فراخوانی `refreshBoard()` — permissionless، هرکسی می‌تواند بزند) با توضیح کوتاه که این تابع نتیجه‌ی رأی‌های فعلی را نهایی می‌کند.

### ۶.۲ اقدامات داخلی هیأت (فقط قابل‌مشاهده/تعامل برای اعضای فعلی هیأت — چک `isBoardMember(address)`)
فهرست اقدامات باز (`executed == false`) با نوع (`RotateOracle`/`ApproveBudget`/`SetEntryThresholdBase`/`SetGrowthFactorPerValidator`/`SetMembershipFeeBps`/`RotateVerifier`)، نصاب (`(boardSize/2)+1`)، و دکمه‌ی رأی (`voteAction(id)`).

فرم ساخت اقدام تازه (فقط برای اعضای هیأت)، یک تب برای هرکدام از شش نوع، دقیقاً با پارامترهای همان تابع `propose*` متناظر در قرارداد.

## ۷. اطلاعات زنده‌ی مشترک (نمایش در همه‌جای داشبورد مربوطه)

- `ValidatorsRegistry.currentEntryThreshold()` — آستانه‌ی ورود فعلی.
- `ValidatorsRegistry.currentMembershipFee()` — کارمزد عضویت فعلی.
- `ValidatorsRegistry.getActiveValidatorCount()`.
- این سه مقدار باید هر ۳۰ ثانیه خودکار رفرش شوند (`refetchInterval`).

## ۸. مدیریت خطا

| خطا | رفتار |
|---|---|
| فراخوان‌کننده عضو/ولیدیتور/عضو هیأت نیست | دکمه‌های اقدام اصلاً نمایش داده نشوند (نه فقط غیرفعال) — چک با `read` قرارداد قبل از رندر فرم |
| رأی تکراری (`already voted`) | قرارداد رد می‌کند؛ پیام فارسی «شما قبلاً رأی داده‌اید» از روی خطای برگشتی تراکنش |
| تراکنش رد شد در کیف‌پول | پیام خنثی «تراکنش لغو شد»، بدون تلاش خودکار مجدد |
| نصاب هنوز کامل نشده بعد از رأی | تراکنش رأی موفق است ولی پیشنهاد `Pending` می‌ماند — پیام «رأی شما ثبت شد، منتظر رأی بقیه» |

## ۹. امنیت

- همه‌ی تراکنش‌ها مستقیم با کیف‌پول کاربر امضا می‌شوند — هیچ سرویس واسط/کلید مشترکی در این داشبورد دخیل نیست.
- فرم «اجرای دلخواه» (`Execute`) باید قبل از ارسال، `data` هگز را در یک ابزار decode ساده (مثلاً تلاش برای تطبیق با ABI شناخته‌شده‌ی قراردادهای پروژه) نمایش دهد تا امضاکننده بفهمد واقعاً چه چیزی امضا می‌کند — حتی اگر decode ناموفق بود، هگز خام باید کامل نمایش داده شود، نه پنهان.

## ۱۰. وابستگی

بلاک اکسپلورر (Blockscout) باید سورس هر شش قرارداد را وریفای کرده باشد — بدونش، گرفتن ABI درست برای این داشبورد سخت‌تر می‌شود (هرچند ABI را می‌توان مستقیم از artifact کامپایل هم گرفت، بدون نیاز به وریفای اکسپلورر؛ وریفای فقط برای شفافیت عمومی لازم است، نه برای کارکرد خودِ این داشبورد).

## ۱۱. سؤالات باز

هیچ سؤال فنی باقی نمانده — همه‌ی توابع، پارامترها، و نصاب‌ها مستقیم از قراردادهای نهایی پروژه گرفته شده‌اند.
