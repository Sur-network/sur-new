# آزمون زندهٔ درگاه پرداخت SurPay با امضاکنندهٔ واقعی SurKMS روی Besu واقعی — دور ۷ («v26-r7-surpay»)

**تاریخ:** ۲۰۲۶-۱۱-۲۳ · **محل:** سرور `192.168.1.210`، ایمیج `hyperledger/besu:26.9.0` (بدون pull) و `postgres:15` (از پیش روی سرور بود؛ بدون pull)، فقط اشیای `sur25w-*`، RPC و PostgreSQL فقط روی `127.0.0.1` با تونل SSH. کلیدها همه آزمایشی. **هیچ کدی (SurPay، SurKMS) تغییر نکرد؛ push انجام نشد؛ زمان زنجیره دست‌کاری نشد.**
**پایه:** SurPay: قرارداد `1f20b50`، سرویس `755ffa4`، وب `28c24a4`، مستند `964bda1`؛ SurKMS `2f524f5`.

## شبکه و اجزا
- ژنسیس واقعی ۱۲ قراردادی (SurPay قرارداد ژنسیس نیست) با GenesisBuilder فعلی، زنجیرهٔ ۲۶۲۰۲۵، بلوک ۱ ثانیه‌ای؛ دو نود Besu (`w1` ولیدیتور، `w2` نود عادی برای خواندن سرویس) و کانتینر `sur25w-pg` (PostgreSQL 15، حجم و حافظهٔ محدود).
- **SurKMS واقعی** (مراسم `init` با `KMS_SURPAY_ADDRESS` و `KMS_INVOICE_TOKENS=native,<توکن permit>`؛ آدرس SurPay از nonce استقرارکننده پیش‌بینی شد، طبق ترتیب تولید: init ← ژنسیس ← استقرار). سه آدرس slotهای زنجیره‌ای در ژنسیس رفت؛ آدرس `invoiceSigner` به سازندهٔ SurPay داده شد. mTLS با گواهی سنجاق‌شده برای سرویس SurPay.
- **سرویس SurPay واقعی** (PostgreSQL، نگهبان زنجیره، webhook، گزارش‌ها) روی PC. قراردادهای آزمایشی: توکن ERC-20 با EIP-2612 (۱۸ رقم اعشار، مجاز) و توکن ساده (۶ رقم، **مجاز نشد**).
- **انحرافات فقط-آزمون (برچسب‌دار):** `SURPAY_ALLOW_INSECURE_TARGETS=1` تا گیرندهٔ webhook و callback محلی با `http://localhost` کار کند (راهنما https و نام میزبان می‌خواهد)؛ اپراتور و تنظیمات تاجر از راه ورود با کیف‌پول تاجر؛ صفحهٔ پرداخت با اسکریپت جایگزین شد (سناریو ۱۰ اجرا نشد). کلید identity oracle و … نقشی ندارند.
- اسکریپت‌ها (BesuLive): `gen-netW.mjs` (دو مرحله)، `server-w/`، `sync-w.sh`، `kms-init-w.mts`، `kms-env-w.sh`، `mk-certs-w.mjs`، `service-env-w.sh`، `start-service-w.sh`، `stop-service-w.ps1`، `lib/w.mts`، `lib/pay.mts`، `w-1-setup.mts`، `w-1b-verify.mts`، `w-2-flow.mts`، `w-4-retry.mts`، `w-5-refusals.mts`، `w-5b-expired.mts`، `w-6-watcher.mts`، `w-6b-verify.mts`، `w-7-delay.mts`، `w-7b-ttl.mts`، `w-9-reports.mts`. اجرا: `NETW=1 node node_modules/tsx/dist/cli.mjs <script>`.

## یافته‌ها و عیب‌ها
هیچ عیب رفتاری در قرارداد، سرویس یا SurKMS پیدا نشد (هر انحراف از انتظار در این دور خطای اسکریپت خودم بود، پایین). **ناسازگاری‌های مستند (بی‌خطر؛ بدون تغییر):**
1. `SurPay/service/README.md` هنوز می‌گوید «SurKMS هنوز `eth_signTypedData_v4` را ندارد» و webhook را با «همان signing secret» امضا می‌داند؛ در عمل SurKMS آن را دارد و webhook با **webhook secret جدا** امضا می‌شود (راهنمای توسعه‌دهنده درست است؛ آزمون ۴٫۲ تفاوت را نشان داد).
2. فاکتور منقضی فقط پس از انقضا **به‌علاوهٔ مهلت ۱۲۰ ثانیه‌ای** در پایگاه‌داده/لیست `expired` می‌آید (طبق راهنما)، ولی بازگشت `NOK` و ردّ زنجیره بلافاصله است؛ تاجری که فوراً پس از انقضا منتظر وضعیت `expired` است ≈ ۲ دقیقه صبر می‌کند.
3. `GET /payments` بدون فیلتر وضعیت همهٔ فاکتورها (شامل `created`/`expired`) را می‌شمارد؛ شمار «پرداخت‌ها» با فیلتر `paid`/`partially_refunded`/`refunded` به‌دست می‌آید.
4. CLI `merchant:add` فقط نام و آدرس می‌گیرد؛ webhook و میزبان callback با ورود کیف‌پول تاجر (`PUT /merchant/settings`) یا API مالک تنظیم می‌شود.

## آنچه آزموده نشد
- **رابط وب** (سناریو ۱۰)، CSP/هدرهای امنیتی در مرورگر؛ TLS و reverse proxy (`TRUST_PROXY`)، محدودیت نرخ هر مسیر.
- همهٔ مواردی که ۷ روز زمان واقعی می‌خواهد: اجرای تغییر کارمزد/دریافت‌کننده/کلید فاکتور، `acceptOwnership`، `ChangeLapsed`، `-13`، چرخش کلید `invoiceSigner` (و `-14`)، کوتاه‌شدن عمر فاکتور پیش از تغییر زمان‌بندی‌شده.
- مدیریت کلید و تاجر: ابطال کلید، چرخش رازها، تعلیق تاجر، API مالک برای ثبت تاجر؛ تاجر قراردادی (پذیرنده با `receive` سنگین)، توکن با کارمزد انتقال، حملهٔ front-run روی `permit`، بازگشت `-59` (ناهمخوانی رویداد با فاکتور).
- بار زیاد/هم‌زمانی، چندنودی، PostgreSQL پایدار و پشتیبان، SurKMS با چند سرور کلاینت، `verify` از چندین تاجر هم‌زمان.
