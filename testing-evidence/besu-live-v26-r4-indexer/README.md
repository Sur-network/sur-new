# آزمون زندهٔ ایندکسر رویدادها (سرویس ۱۸) روی Besu واقعی (دور ۴، «v26-r4-indexer»)

**تاریخ:** ۲۰۲۶-۱۱-۲۳ (اجرا شب ۲۰۲۶-۱۱-۲۲ تا بامداد) · **هدف:** نشان‌دادن این‌که ایندکسر (`Deployments/EventIndexer`، کامیت‌های `6e2486e` تا `e141044` به‌علاوهٔ همین دور) روی Besu واقعی بالای ۵۲۰۰ بلوک تاریخچه را از بلوک ۰ می‌خواند، با شمارندهٔ خود قرارداد می‌خواند، پس از kill و شروع دوباره بدون تکرار و شکاف ادامه می‌دهد و در برابر رد شدن بازه نصف می‌کند.
**محل اجرا: سرور** (`192.168.1.210`، Docker، `hyperledger/besu:26.9.0`، همان ایمیج دورهای قبل، بدون pull)؛ فقط اشیای `sur25i-*`؛ RPC فقط روی `127.0.0.1` سرور و با تونل SSH؛ کلیدها آزمایشی. **هیچ قراردادی و هیچ کد رابطی تغییر نکرد؛ push انجام نشد.** ایندکسر فقط می‌خواند و هیچ تراکنشی نفرستاد.

## شبکه
یک نود Besu (`sur25i-n1`: اولین ولیدیتور = مالک ۱، archive/FOREST)، QBFT، بلوک ۱ ثانیه‌ای، ژنسیس واقعی با ۱۲ قرارداد (ساخته با CLI فعلی GenesisBuilder؛ `genesis-config.json`، `genesis-build.log`)، زنجیرهٔ ۲۶۲۰۲۵. ابزار: `BesuLive/gen-netI.mjs`، `server-i/`، `sync-i.sh`، `router-env-i.sh`. در بلوک ۴۳ مالک ۱ پیشنهاد `proposeKmsFreeze(1,true)` را باز کرد (رویداد `ActionVoted`؛ اجرا نمی‌شود). سپس **Router واقعی + SurKMS** (کلید `distributionOracle` در SurKMS، mTLS) یک توزیع کامل انجام داد (۳ گام؛ `0-router-distribution.out`) ⇒ یک رویداد واقعی `ValidatorRewarded` (۶۳ بلوک) و رویدادهای دورهٔ توزیع. SurKMS پس از توزیع متوقف شد. بعد انتظار تا ارتفاع بالای ۵۲۰۰ (ارتفاع در شروع آزمون ۵۳۳۳).

## نتیجه (`live-test.out`: ۲۴ مرحله، همه PASS؛ اجرای `live/live-test.ts`)
| بخش | نتیجه |
|---|---|
| خط پایه | Besu خودش `eth_getLogs` از ۰ تا `latest` را با `-32005 Requested range exceeds maximum RPC range limit` رد می‌کند؛ بازهٔ ۵۰۰۰ بلوکی را می‌پذیرد |
| خواندن از بلوک ۰ | CLI `sync` با تکهٔ پیش‌فرض ۲۰۰۰: **۳ درخواست**، ۶ رویداد، مکان‌نما روی سر زنجیره |
| نصف‌کردن روی Besu واقعی | با تکهٔ ۶۰۰۰ (فقط در این آزمون، بیش از سقف ۴۰۰۰ تنظیمات) Besu پنجره را رد کرد؛ ایندکسر نصف کرد (`halvings 1`) و **دقیقاً همان ردیف‌ها** را ذخیره کرد (هش یکسان) |
| kill -9 وسط خواندن | با تکهٔ ۵ و یک درخواست هم‌زمان؛ kill وقتی مکان‌نما ۸۱۴ از ۵۳۳۳ بود؛ شروع دوباره از ۸۱۵؛ پایگاه نهایی با خواندن بی‌وقفه **هم‌ارز** (همان هش ردیف‌ها تا همان بلوک، بدون تکرار و شکاف) |
| مقایسه با قرارداد | برای مالک ۱: جمع `rewardShare` = `totalRewardsPaid`، جمع `feeShare` = `totalFeesPaid`، جمع `blocksMined` = `totalBlocksRecorded` (از `getValidatorTotals`)، و `deferred − withdrawn` = `claimable` — هر چهار برابر |
| دورهٔ توزیع | `/rounds/1`: رویداد بسته‌شدن = رکورد `epochs(1)` قرارداد (`totalBlocksMined` ۶۳) |
| آرا | `/votes/owner1` همان `ActionVoted` بلوک ۴۳ را داد |
| سنجش مستقل | شمار `ValidatorRewarded` ایندکسر = شمار یک `eth_getLogs` ساده با تکه‌های ۵۰۰۰ (بدون کد ایندکسر) |
| API واقعی | فرایند `serve` واقعی (`serve-check.txt`): روی `127.0.0.1` گوش می‌دهد، `/health`، `/rewards`، رد POST با ۴۰۵؛ هم‌زمان بلوک‌های تازه را می‌خواند (۵۳۷۸ ← ۵۳۸۲) |

## اندازه‌گیری (`timing.txt`، همان زنجیره، ارتفاع ≈۵۳۵۰–۵۳۶۵، از ماشین ویندوز از راه تونل SSH)
| تکه | هم‌زمانی | درخواست | زمان خواندن و ذخیره (بدون راه‌اندازی Node) |
|---|---|---|---|
| ۲۰۰۰ | ۴ | ۳ | ۱۲۷ ms |
| ۲۰۰۰ | ۱ | ۳ | ۱۰۷ ms |
| ۵۰۰ | ۱ | ۱۱ | ۱۷۱ ms |
| ۱۰۰ | ۱ | ۵۴ | ۶۰۷ ms |
| ۱۰۰ | ۴ | ۵۴ | ۸۸۹ ms |

اوج حافظهٔ فرایند (Node + tsx، کل فرایند) ≈ ۱۵۰ MB؛ زمان کل فرایند `sync` با راه‌اندازی ≈ ۱٫۲ ثانیه. هزینهٔ هر درخواست در این آزمون حدود ۱۰–۱۱ ms بود. **این‌ها اندازه‌گیری در ارتفاع ۵۳۰۰ و با ۶ رویداد است.** برآورد (نه اندازه‌گیری): تعداد درخواست‌ها حدود `ارتفاع ÷ ۲۰۰۰` است؛ در یک میلیون بلوک حدود ۵۰۰ درخواست، یعنی چند ثانیه برای درخواست‌ها، به‌علاوهٔ هزینهٔ ذخیره و خواندن زمان بلوک هر بلوکِ دارای رویداد که با تعداد رویداد زیاد می‌شود و اینجا اندازه‌گیری نشد. هم‌زمانی ۴ روی تونل SSH سریع‌تر از ۱ نشد (تونل تنگنا بود)؛ نتیجه‌ای دربارهٔ شبکهٔ واقعی نمی‌دهد.

## نکتهٔ صادقانه دربارهٔ یک بررسی
مرحلهٔ «Besu بازهٔ ۶۰۰۱ بلوکی را رد می‌کند» با خطای `-32602 Invalid params` رد شد، ولی چون `toBlock = ۶۰۰۰` از سر زنجیره (۵۳۳۳) بالاتر بود، این خطا مربوط به `toBlock` بیرون از زنجیره است، نه سقف بازه (همان تمایزی که در دور ۳ ثبت شد). سقف بازه با مرحلهٔ `0..latest` (`-32005`) و با نصف‌شدن واقعی در مرحلهٔ ۶۰۰۰-بلوکی ثابت می‌شود، پس نتیجه تغییر نمی‌کند؛ ولی آن یک بررسی به‌تنهایی دلیل سقف نیست. اسکریپت را برای ثبت دقیق همان‌طور که اجرا شد نگه داشتم.

## آنچه آزموده نشد
- حجم بزرگ رویداد (فقط ۶ رویداد و یک توزیع)، ارتفاع خیلی بالا (فقط ≈۵۳۰۰)، پایگاه چند صد مگابایتی؛ زمان و حافظه در آن شرایط **اندازه‌گیری نشد**.
- شبکهٔ چندنودی، نود با `--rpc-max-logs-range` غیرپیش‌فرض، RPC عمومی یا پشت پروکسی، تأخیر و قطعی شبکهٔ واقعی؛ API زیر بار یا پشت پروکسی عمومی؛ Postgres.
- قطع نود Besu هنگام خواندن و بازگشت آن روی Besu واقعی (این حالت فقط با آزمون واحد پوشش داده شد).
- اتصال ValidatorApp و GovernanceDashboard به API (کار جداگانه)، و Dockerfile / واحد systemd برای ایندکسر (نوشته نشده).
- فقط Besu `26.9.0` با همین پیکربندی؛ نتیجه آمادگی production یا حسابرسی مستقل نیست.

## اجرا و پاک‌سازی
ساخته‌شده روی سرور: `~/sur25i-live`، شبکهٔ `sur25i-net` (۱۷۲٫۲۹٫۷۸٫۰/۲۴)، حجم `sur25i-n1-data`، کانتینر `sur25i-n1`. حذف با `cleanup.sh` (فقط پیشوند `sur25i-`) و `rm -rf ~/sur25i-live`؛ وضعیت نهایی (`server-cleanup.txt`): ۰ شیء `sur25*`، کانتینرهای سرور ۳۲ (برابر با پیش از شروع). روی PC: SurKMS آزمایشی و تونل SSH متوقف شد.
